# 第二轮复查与性能测量：2026-09-05

这份报告描述 9 月 5 日的固定快照；后续修复及最终构建验证见[提交前复查](pr-review.md)。

本轮对照是[上一轮优化后的版本](performance.md)，不是重新拿最初版本比较。
保留两秒排序尾部、默认 30 秒保存进度、字典先落盘、缺口修正先确认的规则。
没有通过降低采样完整性、放宽认证或延后保存换取性能。

源码快照、旧程序和原始数据保存在本地 `target/perf-review-20260905/`；
汇总和二进制 SHA-256 见 [performance-review-results.json](performance-review-results.json)。
发布程序从 1,054,208 B 增至 1,057,792 B，增加 3,584 B（0.34%）。

## 修复的边界

- **字典编号重用**：字典尾部若丢失，原逻辑可能给新应用分配已被历史记录使用的编号。
  现在启动时流式核验历史日志引用的最大编号，再决定是否能打开或修复字典。
  已引用的条目缺失就停止，不改原件、不返回成功确认。整条与部分条目截断均有回归测试；
  同一端到端测试在旧源码快照中失败，在新版中通过。
- **查询与记录并发**：查询先读字典、后读日志时，可能遇到刚写入的新编号。
  现在仅在遇到未知编号时重新加载字典；仍不存在则明确报错，避免导出成问号或空标题。
  导出失败仍保留原有输出文件。这个修复保证编号解析，不代表多日查询是一份全局瞬时快照。
- **AFK 边界**：已经确认离开后，用户中途活动又再次离开，原逻辑可能漏标这段不确定窗口；
  持续离开后的锁屏采样也可能误报缺口。补齐采样、事件和退出路径，并验证时钟跳变与重复通知。
- **UWP 窗口身份**：子窗口在查询途中销毁、换宿主或 PID 不符时，不再沿用旧进程归属。
  查询前后和标题读取后检查子窗口身份，并把进程句柄保留到最终检查完成。
- **退出与入队竞争**：一个回调已开始取样、尚未入队时收到退出请求，原来的保护范围可能漏掉它。
  现在从取样开始就登记在途工作；已准入的事件完成非阻塞入队，队满则登记缺口，退出等待其收尾。

新增启动核验有实际代价：耗时随历史日志总量增加；任意旧日期的坏文件头或无法认证的首块也会阻止启动。
这是防止未知旧编号被重用的保守选择。扫描按块进行，不把全部历史记录装入内存；
单个逻辑块上限约 17 MiB，动态缓冲容量可能因扩容超过逻辑长度。
字典自身仍会随唯一标题数量增长。

v1 格式仍无法识别恰好位于完整认证块边界的日志尾部截短，也不能证明未认证的损坏尾部里曾有哪些记录。
本轮没有引入新的格式、尾部锚点或外部备份协议。

## 对照方法

同机 Ryzen 9 7945HX、Windows build 26200、Rust 1.97.1，x64 MSVC；
两版均使用 `opt-level=z`、fat LTO、单 codegen unit、strip。
固定回放按旧、新、新、旧顺序运行，编译和真实 daemon 资源采样与回放分开。
旧源码只增加相同的基准入口及回归测试，未修改产品逻辑。

以下均为本机样本中位数，不是跨机器承诺或统计置信区间。
记账计时与分配统计分开；存储和日志基准的计时包含相同的分配计数器开销，
因此它们用于比较这套基准，不能直接当作未插桩程序的耗时。

## 记账：每场景 100,000 条观测

每版 14 次计时。所有场景的完整输出摘要、片段数、缺口数、时长、检查点和无重叠检查一致。

| 场景 | 上一轮 ms | 本轮 ms | 时间变化 | 分配次数：上一轮 → 本轮 |
|---|---:|---:|---:|---:|
| 30 秒采样 | 41.958 | 34.440 | −17.9% | 699,997 → 500,000 |
| 每 2 秒切窗 | 37.319 | 25.182 | −32.5% | 580,000 → 306,668 |
| 每秒 4 次标题变化 | 38.141 | 35.117 | −7.9% | 401,665 → 327,503 |
| 每秒 400 条顺序事件 | 23.274 | 23.825 | +2.4% | 201,254 → 200,758 |

主要改动是直接接管已有的结果缓冲，省去转交过程中重新分配和搬移。
普通切窗的累计分配量从 111,520,345 B 降为 15,307,481 B（−86.3%）；这是累计分配量，不是驻留内存。

高频压力场景本轮基本持平。Accounting 大小仍为 296 B，队列上限没有增加。

## 窗口解析：每次 20,000 次调用

每版每种配置 10 次计时，使用私有不可见窗口，不切换前台、不注入输入。
每次均解析成功；开始前核对完整标题。这里是同一存活进程的重复解析，不代表跨进程切换吞吐。

| 场景 | 上一轮 ms | 本轮 ms | 时间变化 |
|---|---:|---:|---:|
| 短标题，采集关闭 | 6.961 | 7.167 | +3.0% |
| 短标题，采集开启 | 16.752 | 14.229 | −15.1% |
| 长标题，采集关闭 | 6.878 | 7.281 | +5.9% |
| 长标题，采集开启 | 171.287 | 128.691 | −24.9% |

默认标题直接使用栈缓冲，一次读取；长标题保留动态缓冲。
省去了预先查询标题长度和临时字符串中转，每次仍读取当前标题。关闭标题时没有进一步提速。

## 历史日志：65,536 条记录，热缓存

样本为 2,048 个块、每块 32 条记录，共 1,179,664 B；每版 18 次计时。
读取和查询均逐字段计算摘要，结果一致，查询同时核对没有缺口或损坏。
重开和启动测试验证操作成功；这两个操作本身不重复生成记录摘要。

| 操作 | 上一轮 ms | 本轮 ms | 分配次数：上一轮 → 本轮 |
|---|---:|---:|---:|
| 读取 | 6.824 | 6.967 | 4,110 → 15 |
| 查询 | 8.872 | 8.792 | 4,165 → 55 |
| 重开日志 | 12.257 | 6.572 | 8,209 → 14 |
| writer 启动 | 1.300 | 7.747 | 46 → 74 |

读写复用同一块加密缓冲，读取只在认证成功后暴露明文；没有缺口的查询直接复用原记录集合。
读取与查询耗时基本持平，累计分配量分别减少约 47% 和 30%；查询峰值堆仍为 4,194,446 B。
重开日志复用已经核验的文件句柄，避免第二遍解密，耗时减少约 46.4%。
只读的损坏文件仍可保留原件并写入新分片，这个恢复分支有专门测试。

**启动增加约 6.447 ms，约为旧版的 5.96 倍**，原因是新增历史编号核验。
这个样本的启动峰值 Rust 堆仅增加 291 B；更大的历史库需按实际大小测量启动时间。

| 场景 | 上一轮 ms | 本轮 ms | 确认时存活 Rust 堆：上一轮 → 本轮 |
|---|---:|---:|---:|
| 重复标题 | 141.335 | 151.648 | 71,222 → 69,046 B |

## 真实 daemon 常驻占用

同一桌面同时运行两版，预热 5 秒后采样 64 秒，默认设置和标题开启各重复两轮。
八个实例均获得真实前台窗口并写入应用字典，托盘正常，标准错误为空，正常退出且未被强制结束。
以下范围是两轮的结果范围；工作集和私有提交使用各轮中位数，CPU 和 I/O 使用各轮累计量。

| 指标 | 上一轮 | 本轮 |
|---|---:|---:|
| 默认工作集 MiB | 12.72–13.18 | 12.72–13.18 |
| 默认私有提交 MiB | 2.10–2.11 | 2.09 |
| 默认 CPU ms / 64 秒 | 0 | 0–15.625 |
| 默认 CPU cycles / 百万 | 11.96–18.36 | 10.20–18.37 |
| 默认请求写入 B / 64 秒 | 170–392 | 170–392 |
| 标题开启工作集 MiB | 12.70–12.72 | 12.70–12.74 |
| 标题开启私有提交 MiB | 2.07–2.08 | 2.08–2.09 |
| 标题开启 CPU ms / 64 秒 | 218.750–296.875 | 281.250–312.500 |
| 标题开启 CPU cycles / 百万 | 724.03–842.22 | 758.14–886.26 |
| 标题开启请求写入 B / 64 秒 | 191–567 | 191–567 |

**本轮没有取得整体 CPU 降幅。** 标题开启时，配对 cycles 分别增加约 4.7% 和 5.2%；
必要的退出保护扩大到整个取样过程，窗口解析虽更快，也不能据此声称进程整体更省 CPU。
本次没有单独拆分各改动的因果贡献，两轮自然桌面样本也不足以断定长期差异。
默认配置接近 CPU 时间计量分辨率；零读数不等于零工作。

工作集包括共享驻留页面，私有提交不是私有驻留内存；第一轮两版工作集都高于后续轮次，
应比较同轮配对数据，不能把旧报告的单个数值直接当成本轮基线。
I/O 是进程请求量，不是物理磁盘写入量。完整逐轮统计和退出结果保存在 JSON 汇总中。

## 验证与复现

调试版与发布版各 **119 项测试通过**（111 库测试、1 程序测试、3 数据完整性测试、4 隔离端到端测试）；
Clippy `-D warnings`、修改文件的 rustfmt 检查和 `git diff --check` 通过。
测试覆盖损坏原件、旧格式兼容、认证失败、字典同步失败、跨日、迟到事件和退出确认。
没有实际执行系统注销、睡眠或锁屏；这些状态边界通过确定性测试验证。

```powershell
cargo test --locked --all-targets
cargo test --release --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo run --release --locked --example accounting_perf -- 100000
cargo run --release --locked --example storage_perf -- 4000 2
cargo run --release --locked --example resolver_perf -- 20000
cargo run --release --locked --example resolver_perf -- 20000 4096 40
cargo run --release --locked --example log_perf -- 2048 9
```

对照时分别构建源码快照，并交替直接运行构建好的程序，避免把编译时间混入测量。
真实 daemon 资源测试沿用 `scripts/measure-resources.ps1`，使用独立临时数据和命名对象。
