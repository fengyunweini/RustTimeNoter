# 性能与资源测量：2026-09-05

本文保留第一轮测量。后续优化见[第二轮复查报告](performance-review.md)，9 月 7 日快照见[提交前复查](pr-review.md)。

本轮优化保留两秒事件排序尾部、缺口修正、30 秒默认保存进度，以及字典先于日志持久化的要求。
主要收益来自减少数据搬移、重复查询、重复字符串和同步磁盘次数。

- `before`：上一轮可靠性实现，性能优化开始前保存的源码和发布程序。

- 所有数据使用独立临时目录。没有安装、自启动、键鼠注入、切换用户焦点或强制修剪工作集。

汇总及二进制 SHA-256 保存在 [performance-results.json](performance-results.json)。原始逐秒数据和优化前源码快照保留在本地 `target/perf-20260905/`。

## 常驻进程

三个真实 daemon 在同一桌面同时运行，预热 5 秒，再每秒采样一次、持续 64 秒。
分别测试默认设置和开启标题，各重复两轮；测量期间停止编译和压力回放。启动与退出不计入 CPU/I/O 增量。

CPU 时间存在约 15.625 ms 的计量粒度：

## 固定输入回放

### 计时内核

每场景 100,000 条观察，两轮共 14 次计时，以下为合并中位数。
轨迹预先构造，计时包含输入副本、聚合、输出消费和释放；分配统计与内容校验在独立未计时的回放中完成。

| 场景 | 优化前 ns/条 | 优化后 ns/条 | 耗时降低 |
|---|---:|---:|---:|
| 每 30 秒采样 | 508.9 | 414.7 | 18.5% |
| 每 2 秒切窗 | 517.4 | 366.9 | 29.1% |
| 每秒 4 次标题变化 | 558.7 | 392.8 | 29.7% |
| 每秒 400 次有序压力 | 1340.2 | 238.7 | 82.2% |
| 每秒 400 次、最多迟到 160 ms | 1389.7 | 349.5 | 74.9% |

所有场景的完整输出摘要、累计时长、片段数和 checkpoint 数一致，没有缺口或重叠。
压力场景待处理事件上界 865，未触发 1024 容量上限。两秒尾部没有缩短。
计时对象本身从 360 降至 296 字节；普通切窗的分配次数从 953,336 降至 580,000。
这里的速度改善只适用于计时内核，不等于整个 daemon 的 CPU 按相同比例下降。

### 写入与字典

每轮向真实 writer 重放 4000 条记录、16 个应用，每 128 条等待一次持久化确认；各场景 3 轮。
标题长度固定，比较 128 个重复标题和 4000 个唯一标题。密钥/目录初始化及输入构造不计时。
计时包含队列、字典写入、日志加密及最终同步；分配器计数在两个版本中都开启。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 4000 个唯一标题写入中位数 | 16107.5 ms | 283.6 ms | 耗时降低 98.2% |
| 128 个重复标题写入中位数 | 733.5 ms | 140.3 ms | 耗时降低 80.9% |
| 唯一标题场景，确认保存后的存活堆 | 1,548,982 B | 950,582 B | 降低 38.6% |
| 唯一标题场景，分配次数 | 16,307 | 8,214 | 降低 49.6% |
| 唯一标题场景，最终文件大小 | 673,750 B | 673,750 B | 一致 |
| 重复标题场景，最终文件大小 | 89,078 B | 89,078 B | 一致 |

存活堆由基准的 Rust 分配器统计，包含基准进程仍存活的分配，不是整个 daemon 的工作集。
记录数和累计时长均保持一致。AES 随机 nonce 不同，因此比较文件长度和解密后的记录，不能比较密文字节相等。

### 重复窗口解析

每种设置每次解析 20,000 次，预热 1000 次；按 before/after/after/before 顺序执行，两轮共 10 次的中位数。

| 设置 | 优化前 us/次 | 优化后 us/次 | 耗时降低 |
|---|---:|---:|---:|
| 标题关闭 | 33.279 | 0.367 | 98.9% |
| 标题开启 | 42.688 | 0.868 | 98.0% |

优化前快照只加了一个无状态调用适配器，以便运行同一个基准入口；实际仍每次执行原来的窗口解析。

基准创建私有、不可见的 message-only 窗口，始终解析同一存活进程；标题开启时每次仍查询标题。
它测量的是重复解析热路径，不代表不同进程之间不停切换时的收益。缓存只保留一个进程句柄，
每次校验进程存活和窗口归属；UWP 子进程重新解析，避免复用宿主上次的子进程信息。

## 改动与边界

1. 待处理队列使用环形结构，通常按顺序到达时直接追加，乱序时才查找插入位置；移除队首不再搬移整段。
2. 关闭片段时转移已有字符串，去掉重复持有的应用信息；字典两个索引共享一份字符串。
3. 新字典项成批同步。写入任何引用日志之前先同步两本字典，失败就停止；缺口修正仍先确认保存。
4. 写入器没有待保存数据时阻塞等待，有数据时保留刷新期限；持续消息也不能饿死定时刷新。
5. 复用有界加密缓冲，重复窗口查询使用一个有进程寿命校验的缓存。直接查询可执行文件采用
   [Microsoft 推荐的 API](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getmodulefilenameexw)。

本轮没有延长保存间隔，也没有压缩或删减数据。最终文件大小没有下降；减少的是同步次数和处理开销。
默认一直使用同一应用时，每 30 秒单条 checkpoint 的日志开销约 49 B（17 B 记录 + 32 B 加密封装），
连续 8 小时约 46 KiB，另加文件头及字典；这是格式推算，不是整天实测。
字典总内存仍会随唯一标题数量增长；缓冲有上限不等于整个进程内存固定。

## 复现

```powershell
cargo build --release --locked
cargo run --release --locked --example accounting_perf -- 100000
cargo run --release --locked --example storage_perf -- 4000 3
cargo run --release --locked --example resolver_perf -- 20000
pwsh -File scripts/measure-resources.ps1 -OptimizedExe target/release/tracker.exe -Scenario Both -RequireDesktop
```

三版本配对时，额外传入 `-MasterExe`、`-BeforeExe`。脚本拒绝没有测试隔离标记的程序；
原版 master 必须先在源码副本中仅改两个命名对象常量，不能拿正式实例参加基准。
回放应在同机、相同构建参数下各重复多次，且与进程空闲测量分开运行。

验证：调试版与发布版各 100 项测试通过，Clippy `-D warnings` 通过。
新增的字典同步故障测试使用真实只读句柄，检查同步失败时不会写入引用日志；已有缺口、迟到事件、
损坏原件保护、跨日和退出确认测试均继续通过。
